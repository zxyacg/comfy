# 架构决策记录

> 本目录用于记录本项目的**重要架构决策**。
>
> 每当需要做跨越模块边界、影响向后兼容性或修改核心数据结构的决策时，
> 应该在此记录，以便未来的 AI 开发者了解"为什么这么做"。

## 决策记录模板

当需要做一次架构决策时，按以下格式创建文件 `docs/DECISIONS/YYYY-MM-DD-<简短标题>.md`：

```markdown
# 决策：<决策标题>

## 日期
YYYY-MM-DD

## 为什么修改
描述当前架构遇到了什么问题或需求。

## 修改前方案
描述修改前的方案、模块结构和数据流。

## 修改后方案
描述修改后的方案、模块结构和数据流。

## 为什么选择新方案
列出选择新方案的理由，包括：
- 技术考量
- 与现有架构的兼容性
- 迁移成本
- 长期维护影响

## 对现有模块的影响
列出受影响的模块和影响范围：

| 模块 | 影响 | 是否需要修改 |
|------|------|-------------|
| `lib/xxx` | 函数签名变化 | 是 |
| `nodes/xxx` | 输入参数变化 | 是 |
| `templates/*.json` | 数据格式变化 | 是 |
| `tests/xxx` | 测试用例需更新 | 是 |

## 向后兼容性
- [ ] 完全向后兼容
- [ ] 需要迁移脚本
- [ ] 破坏性变更（需大版本号）

## 相关讨论
- Issue/PR 链接
- 相关文档链接
```

## 何时需要记录决策

以下情况**必须**记录决策：

1. **修改核心数据结构**：`Zone`、`Template` dataclass 的字段变更
2. **修改公共接口签名**：任何 `lib/` 导出函数的参数变更
3. **增加新的模块层级**：如增加 Service 层、Store 层
4. **增加外部依赖**：引入新的 Python 包或前端库
5. **改变依赖方向**：违反当前 ARCHITECTURE.md 中的依赖约束
6. **重构现有模块**：拆分或合并已有模块
7. **引入新的通信机制**：HTTP API、WebSocket、IPC 等
8. **修改数据格式**：JSON 模板格式变更、图片格式变更

## 原则

1. **不要记录"怎么做"** — 记录"为什么这么做"
2. **不要记录 UI 细节** — 记录模块边界和数据流
3. **不要只记录正面理由** — 也要记录放弃的方案和理由
4. **简洁但完整** — 让未来的 AI 开发者能在 5 分钟内理解上下文
